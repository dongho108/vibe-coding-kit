# /feature 기능 추가와 수정

서비스가 한 번 결제까지 돌고 나면, 사용자는 계속 뭔가를 더하거나 고치고 싶어진다.
이 스킬은 그 요청을 받을 때마다 **크기를 먼저 재고**, 크기에 맞는 절차로 진행한다.
절차가 달라도 **검증은 항상 끝까지 돌린다.**

## 쓸 것

| 쓸 것 | 언제 |
|---|---|
| `plan` 의 원칙 | 큰 기능의 기획. 범위를 깎는다 |
| `design-system/<slug>/MASTER.md`, `design` 의 원칙 | 새 화면을 기존 디자인과 똑같이 맞출 때 |
| `nextjs-best-practices`, `nextjs-developer` | 화면·라우트 코드 |
| `supabase`, `supabase-postgres-best-practices` | 테이블·권한(RLS)을 바꿀 때 |
| `pay` | 결제·환불과 닿는 기능. `pay` 의 0단계(토스 문서 읽기)부터 따른다 |
| `agent-browser`, `next-dev-loop`, `webapp-testing` | 검증 |
| `web-design-guidelines` | 큰 기능의 QA에서 화면 점검 |

## 시작 전에

1. `package.json` 과 `app/` 이 있는지 본다. 없으면 이 스킬이 아니다. `/start` 부터 안내한다.
2. `docs/기획서.md` 와 `design-system/*/MASTER.md` 를 읽는다. 지금 서비스가 뭔지, 어떤 모양인지 알고 시작한다.
3. `git status` 가 깨끗한지 본다. 커밋 안 된 변경이 있으면 먼저 사용자에게 묻고 커밋해둔다.
   **기능마다 커밋을 따로 남겨야 문제가 생겼을 때 그 기능만 되돌릴 수 있다.**

## 크기 판단

아래 중 **하나라도** 해당하면 큰 기능이다. 하나도 없으면 작은 수정이다.

| 큰 기능 신호 | 예 |
|---|---|
| 새 페이지나 새 화면 흐름이 생긴다 | 마이페이지, 관리자 페이지, 리뷰 작성 화면 |
| 저장할 것이 늘어난다 (새 테이블·새 컬럼) | 리뷰, 쿠폰, 찜, 알림 설정 |
| 로그인·권한·결제·환불과 닿는다 | 쿠폰 할인, 환불 버튼, 관리자만 보이는 메뉴 |
| 새 외부 서비스나 새 키가 필요하다 | 이메일 발송, 카카오 알림톡, 지도 |
| 화면 여러 곳이 같이 바뀐다 | 가격 정책 변경, 회원 등급 |

작은 수정의 예: 문구·색·간격·사진 바꾸기, 버튼 하나 추가(기존 동작 연결), 목록 정렬 순서, 눈에 보이는 버그 하나 고치기.

판단 결과를 **한 줄로** 말하고 바로 진행한다. 묻지 않는다.

```
작은 수정이라 바로 고칠게요.
```
```
새로 저장할 게 생기는 큰 기능이라, 기획 → 디자인 → 개발 → 확인 순서로 갈게요.
```

사용자가 "그냥 바로 해줘"라고 하면 따르되, **결제·로그인·권한과 닿는 기능은 절차를 줄이지 않는다.**
이유를 한 줄로 말한다. "돈이나 개인정보와 닿는 부분이라 확인 단계는 꼭 거칠게요."

작은 수정으로 시작했는데 하다 보니 큰 기능 신호가 나오면, 멈추고 큰 기능 절차로 바꾼다고 말한다.

## 작은 수정

1. 고친다. 요청한 것만 고친다. 옆에 보이는 다른 것까지 손대지 않는다.
2. 아래 **검증**의 기본 검증을 돌린다.
3. 바뀐 화면 스크린샷을 보여주고 커밋한다.

## 큰 기능

단계마다 사용자에게 결과를 보여주고 **확인을 받은 뒤** 다음 단계로 간다.

### 1. 기획

`plan` 의 원칙 그대로 **범위를 깎는다.** "그건 다음에 추가할 수 있어요"가 기본 대사다.
한 번에 하나만 묻고, 모르면 대신 정하고 확인만 받는다. 기술 용어를 쓰지 않는다.

`docs/기획서.md` 맨 아래 `## 추가 기능` 절에 이어서 적는다. (절이 없으면 만든다)

```markdown
### <기능 이름> (YYYY-MM-DD)
- 왜: 누가 어떤 불편 때문에 쓰는가 (한 줄)
- 화면: 새로 생기거나 바뀌는 화면 (최대 2개)
- 저장할 것: 새로 저장하는 것 (없으면 "없음")
- 하지 않는 것: 이번에 안 넣기로 한 것
- 확인할 것: QA에서 눌러볼 시나리오 3개 이내
```

"확인할 것"은 QA 단계의 체크리스트가 된다. 여기서 사용자와 합의한다.

### 2. 디자인

- 새 화면은 `design-system/*/MASTER.md` 와 기존 화면의 컴포넌트·간격·글꼴을 **그대로** 쓴다. 새 색을 만들지 않는다.
- 기본 디자인(Your Next Store 스타일)으로 만든 서비스면 `design` 스킬의 `references/yns/` 에서 비슷한 화면을 찾아 옮긴다.
- 필요한 shadcn 컴포넌트가 없으면 그것만 `npx shadcn@latest add <이름>` 으로 받는다.
- 먼저 **가짜 데이터로 화면만** 만들고, 데스크톱과 모바일 폭(390px) 스크린샷을 보여준다.
  "이 모양으로 갈게요, 괜찮으세요?" 확인을 받는다.

### 3. 개발

- 저장할 것이 늘면 Supabase MCP로 마이그레이션을 만든다. **새 테이블에는 RLS를 반드시 켜고** 정책을 같이 만든다.
  남의 데이터를 읽거나 고칠 수 없는지가 기준이다.
- 비밀 키가 새로 필요하면 `.env.local` 에만 넣고, 배포 때 Vercel 환경변수에도 넣어야 한다고 적어둔다.
  `NEXT_PUBLIC_` 은 브라우저에 보여도 되는 값에만 붙인다.
- 결제·환불과 닿으면 `pay` 스킬의 규칙(서버에서 금액 대조, 시크릿 키는 서버에서만)을 그대로 지킨다.
- 가짜 데이터를 실제 데이터로 바꾼다. 가짜 데이터 파일이 남지 않게 정리한다.

### 4. QA

아래 **검증**의 기본 검증과 큰 기능 검증을 모두 돌린다.
기획서의 "확인할 것" 시나리오를 하나씩 눌러보고 결과를 표로 보여준다.

```
| 확인할 것 | 결과 |
|---|---|
| 로그인한 사람만 리뷰를 쓸 수 있다 | 통과 |
| 남의 리뷰는 지울 수 없다 | 통과 |
| 모바일에서 별점을 누를 수 있다 | 통과 |
```

## 검증

**사용자가 시키지 않아도 항상 돌린다.** 통과하기 전에는 "다 됐어요"라고 말하지 않는다.

### 기본 검증 (작은 수정, 큰 기능 모두)

```bash
npx tsc --noEmit
npm run lint
npm run build
```

- 셋 중 하나라도 실패하면 고치고 처음부터 다시 돌린다. (`package.json` 에 `lint` 스크립트가 없으면 그 줄만 건너뛴다)
- `npm run dev` 를 띄우고 `agent-browser` 로 바뀐 화면을 연다 (`next-dev-loop` 의 방식).
  - 데스크톱 폭과 모바일 폭(390px) 스크린샷을 찍어 직접 본다. 깨진 곳이 없는지, 요청한 대로 바뀌었는지.
  - 브라우저 콘솔에 에러가 없는지 본다.
- 바뀐 화면을 쓰는 핵심 흐름이 여전히 되는지 한 번 눌러본다. 예: 상품 카드 문구를 바꿨으면 상품 상세로 넘어가는지.

### 큰 기능 검증 (추가)

- 기획서의 "확인할 것" 시나리오를 `agent-browser` 로 끝까지 눌러본다.
- 권한을 확인한다. 로그아웃 상태, 다른 사용자로 접근했을 때 막히는지.
- DB를 바꿨으면 Supabase MCP의 `get_advisors` (security) 로 RLS 빠진 테이블이 없는지 본다.
- **기존 핵심 흐름이 안 깨졌는지** 처음부터 눌러본다. 랜딩 → 로그인 → 상품(요금제·예약) 선택 → 테스트 결제 승인.
  결제와 닿지 않은 기능이어도 한다. 공용 컴포넌트를 건드리면 엉뚱한 곳이 깨진다.
- `web-design-guidelines` 로 새 화면을 훑는다.

### 실패했을 때

- 고치고 검증을 처음부터 다시 돌린다. 같은 문제로 세 번 실패하면 멈추고,
  무엇이 안 되는지와 시도한 것을 사용자에게 쉬운 말로 설명한 뒤 어떻게 할지 묻는다.
- 검증을 건너뛰거나, 실패한 채로 커밋하지 않는다. `--no-verify` 도 쓰지 않는다.

## 끝

검증을 통과하면 커밋한다. 커밋 메시지는 한국어로 무엇을 바꿨는지 한 줄.

```bash
git add -A && git commit -m "<무엇을 바꿨는지>"
```

`/build` 가 깔아둔 커밋 검사기가 비밀 키를 한 번 더 막는다.

**푸시는 묻고 한다.** Vercel이 GitHub와 연결돼 있으면 푸시하는 순간 실제 사이트가 바뀐다.

```
다 됐어요. 확인한 것: (검증 결과 요약)
실제 사이트에도 올릴까요? 올리면 1~2분 뒤에 반영돼요.
```

새 비밀 키를 추가했으면 푸시 전에 Vercel 환경변수에 넣었는지 먼저 확인한다. 없으면 배포된 사이트만 깨진다.
