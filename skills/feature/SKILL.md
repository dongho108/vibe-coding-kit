# /feature 기능 추가와 수정

서비스가 한 번 결제까지 돌고 나면, 사용자는 계속 뭔가를 더하거나 고치고 싶어진다.
이 스킬은 그 요청을 받을 때마다 **크기를 먼저 재고**, 크기에 맞는 절차로 진행한다.
절차가 달라도 **코드보다 테스트를 먼저 쓰고, 검증은 항상 끝까지 돌린다.**
테스트는 파일로 남기 때문에, 기능이 늘어날수록 예전 기능이 깨졌는지를 `npm test` 한 번으로 알 수 있다.

## 진행 기록

시작할 때 `.claude/worklog/진행상황.md` 를 읽고 (없으면 만들고), **단계 하나를 끝낼 때마다** 고친다.
형식과 규칙은 `next` 스킬의 "작업 기록 파일" 을 따른다. 이미 "정해진 것" 에 있는 선택은 다시 묻지 않는다.
큰 기능은 시작할 때 "남은 일" 에 올리고, 검증까지 끝나면 체크한다. 사용자가 "나중에" 라고 미룬 요청도 "남은 일" 에 적는다.

## 쓸 것

| 쓸 것 | 언제 |
|---|---|
| `plan` 의 원칙 | 큰 기능의 기획. 범위를 깎는다 |
| `design-system/<slug>/MASTER.md`, `design` 의 원칙 | 새 화면을 기존 디자인과 똑같이 맞출 때 |
| `nextjs-best-practices`, `nextjs-developer` | 화면·라우트 코드 |
| Supabase MCP | 데이터베이스 확인·변경 전부. `build` 스킬의 "Supabase MCP 사용 규칙"을 따른다. 아직 연결 안 됐으면 그 절의 연결 절차부터 |
| `supabase`, `supabase-postgres-best-practices` | 테이블·권한(RLS)을 설계할 때 |
| `pay` | 결제·환불과 닿는 기능. `pay` 의 0단계(토스 문서 읽기)부터 따른다 |
| Vitest | 금액 계산·권한 판단 같은 로직 테스트 |
| Playwright (`@playwright/test`) | 화면 흐름 테스트. 기획서 "확인할 것" 시나리오 |
| `agent-browser`, `next-dev-loop`, `webapp-testing` | 눈으로 보는 검증 (스크린샷·디자인·모바일). `webapp-testing` 의 파이썬 스크립트는 한 번 확인하고 버리는 용도, 남길 테스트는 위의 TS Playwright 로 쓴다 |
| `web-design-guidelines` | 큰 기능의 QA에서 화면 점검 |

## 시작 전에

1. `package.json` 과 `app/` 이 있는지 본다. 없으면 이 스킬이 아니다. `/start` 부터 안내한다.
2. `docs/기획서.md` 와 `design-system/*/MASTER.md` 를 읽는다. 지금 서비스가 뭔지, 어떤 모양인지 알고 시작한다.
   데이터와 닿는 요청이면 Supabase MCP의 `list_tables` 로 지금 테이블 구조도 본다. 기억이나 추측으로 컬럼 이름을 쓰지 않는다.
3. `git status` 가 깨끗한지 본다. 커밋 안 된 변경이 있으면 먼저 사용자에게 묻고 커밋해둔다.
   **기능마다 커밋을 따로 남겨야 문제가 생겼을 때 그 기능만 되돌릴 수 있다.**
4. `package.json` 에 `test` 스크립트가 없으면 아래 **테스트 준비**부터 한다.

## 테스트 준비 (처음 한 번)

끝나면 진행상황.md 의 "정해진 것" 에 `테스트: Vitest + Playwright` 를 적는다. 준비만 따로 커밋한다.

```bash
npm i -D vitest @vitejs/plugin-react vite-tsconfig-paths jsdom @testing-library/react @testing-library/jest-dom @playwright/test
npx playwright install chromium
```

- `vitest.config.ts`: `environment: 'jsdom'`, 플러그인 `react()`·`tsconfigPaths()` (`@/` 경로), `include: ['**/*.test.{ts,tsx}']`, `exclude` 에 `e2e/**`·`node_modules/**`.
- `playwright.config.ts`: `testDir: 'e2e'`, `webServer: { command: 'npm run dev', port: 3000, reuseExistingServer: true }`,
  프로젝트 두 개 — 데스크톱(`Desktop Chrome`)과 모바일(`viewport: { width: 390, height: 844 }`). `trace: 'retain-on-failure'`.
- `package.json` scripts: `"test": "vitest run"`, `"test:e2e": "playwright test"`.
- `.gitignore` 에 `test-results/`, `playwright-report/`.

**로그인·결제·DB처럼 큰 것은 모킹한다**

구글 로그인, 토스 결제, Supabase는 테스트에서 진짜로 부르지 않는다. 자동으로 누를 수 없고, 실제 사이트와 같은 데이터베이스를 쓰기 때문이다.
대신 그 경계를 가짜로 바꿔 끼우고, **우리 코드가 그 결과를 받아 제대로 하는지**만 테스트한다.

- 로그인·권한은 Vitest에서 `vi.mock('@/lib/supabase/server')` 로 `createClient` 를 가짜로 바꾼다.
  `auth.getUser()` 가 로그아웃(`user: null`) / 사용자 A / 사용자 B 를 돌려주게 해두고, 서버 액션을 그냥 함수처럼 불러 결과를 본다.
  예: B로 A의 리뷰 삭제 액션을 부르면 거절되고 `delete` 가 불리지 않는다.
- DB 조회·저장도 같은 가짜 클라이언트에서 `from().select()` 등이 정해둔 행을 돌려주게 한다. 테스트가 실제 DB에 쓰지 않는다.
- 토스 API는 `vi.spyOn(globalThis, 'fetch')` 로 승인 성공·실패 응답을 정해두고, 금액 대조·실패 처리를 본다.
- `next/cache` (`revalidatePath`)·`next/navigation` (`redirect`) 도 `vi.mock` 으로 막는다. 서버 쪽 테스트 파일 맨 위에 `// @vitest-environment node`.
- 가짜 사용자·가짜 클라이언트는 `test/mocks/supabase.ts` 한 곳에 만들어 재사용한다. 테스트마다 새로 만들지 않는다.
- Playwright는 로그인이 필요 없는 화면(랜딩·상품 목록·로그아웃 상태에서 막히는지)만 진짜로 돌린다.
  로그인한 화면의 모양은 `agent-browser` 로 사용자의 실제 로그인 상태에서 스크린샷으로 본다.
- **앱 코드에 테스트용 로그인 주소나 "테스트면 통과" 같은 우회 코드를 넣지 않는다.** 실제 사이트에도 그대로 올라가 구멍이 된다. 가짜는 테스트 파일 안에만 둔다.
- 모킹은 RLS(데이터베이스 권한)를 확인하지 못한다. 그래서 DB를 바꾼 기능은 아래 **큰 기능 검증**의 `get_advisors`·`execute_sql` 확인을 그대로 한다.

## 테스트 먼저 (TDD)

작은 수정과 큰 기능 모두 이 순서로 만든다. **빨강 → 초록 → 정리.**

1. "이렇게 돼야 한다" 를 테스트로 먼저 쓴다.
   - 로직(금액·권한·날짜 계산 등)은 `lib/` 의 순수 함수로 빼고 옆에 `*.test.ts` 로. 서버 액션·서버 컴포넌트 안에 로직을 묻어두면 테스트할 수 없다.
   - 화면 흐름은 `e2e/<기능>.spec.ts` 로. 요소는 `getByRole`·`getByText`·`getByLabel` 로 찾는다 (화면 문구 그대로라 읽기 쉽다). 안 되면 그때만 `data-testid`.
2. 돌려서 **실패하는 걸 확인한다. 실패 이유가 "아직 안 만들어서" 여야 한다.**
   오타·import·설정 문제로 실패하면 테스트부터 고친다. 처음부터 통과하면 아무것도 확인하지 못하는 테스트이니 고친다.
3. 테스트를 통과할 만큼만 만든다.
4. 통과하면 코드를 정리하고 다시 돌린다.
5. **테스트를 통과시키려고 테스트를 고치거나 지우지 않는다.** 기획이 바뀌어서 기대가 달라진 경우에만, 사용자에게 말하고 고친다.

사용자에게는 쉬운 말로 한 줄씩 알린다.

```
먼저 "로그인 안 하면 리뷰를 쓸 수 없다" 를 테스트로 적었어요. 아직 안 만들어서 실패하는 게 맞아요.
만들고 다시 돌렸더니 통과했어요.
```

## 크기 판단

아래 중 **하나라도** 해당하면 큰 기능이다. 하나도 없으면 작은 수정이다.

| 큰 기능 신호 | 예 |
|---|---|
| 새 페이지나 새 화면 흐름이 생긴다 | 마이페이지, 관리자 페이지, 리뷰 작성 화면 |
| 저장할 것이 늘어난다 (새 테이블·새 컬럼) | 리뷰, 쿠폰, 찜, 알림 설정 |
| 로그인·권한·결제·환불과 닿는다 | 쿠폰 할인, 환불 버튼, 관리자만 보이는 메뉴 |
| 새 외부 서비스나 새 키가 필요하다 | 이메일 발송, 카카오 알림톡, 지도 |
| 화면 여러 곳이 같이 바뀐다 | 가격 정책 변경, 회원 등급 |

작은 수정의 예: 문구·색·간격·사진 바꾸기, 버튼 하나 추가(기존 동작 연결), 목록 정렬 순서, 눈에 보이는 버그 하나 고치기.

판단 결과를 **한 줄로** 말하고 바로 진행한다. 묻지 않는다.

```
작은 수정이라 바로 고칠게요.
```
```
새로 저장할 게 생기는 큰 기능이라, 기획 → 디자인 → 개발 → 확인 순서로 갈게요.
```

사용자가 "그냥 바로 해줘"라고 하면 따르되, **결제·로그인·권한과 닿는 기능은 절차를 줄이지 않는다.**
이유를 한 줄로 말한다. "돈이나 개인정보와 닿는 부분이라 확인 단계는 꼭 거칠게요."

작은 수정으로 시작했는데 하다 보니 큰 기능 신호가 나오면, 멈추고 큰 기능 절차로 바꾼다고 말한다.

## 작은 수정

1. **테스트 먼저.** 위 **테스트 먼저 (TDD)** 순서대로, 바뀔 모습을 테스트로 적고 실패를 확인한다.
   - 버그: 버그가 나는 상황을 그대로 재현하는 테스트. 지금은 실패해야 한다.
   - 문구·버튼·정렬: Playwright로 바뀐 문구, 버튼을 눌렀을 때 동작, 목록 순서를 확인한다.
   - 색·간격·사진: Playwright의 `toHaveCSS` (색·크기) 나 `toHaveAttribute('src', ...)` 로 확인한다.
     스크린샷 비교(`toHaveScreenshot`)는 컴퓨터마다 결과가 달라 쓰지 않는다.
2. 고친다. 요청한 것만 고친다. 옆에 보이는 다른 것까지 손대지 않는다. 테스트가 통과할 때까지.
3. 아래 **검증**의 기본 검증을 돌린다.
4. 바뀐 화면 스크린샷을 보여주고 커밋한다. 테스트 파일도 같이 커밋한다.

## 큰 기능

단계마다 사용자에게 결과를 보여주고 **확인을 받은 뒤** 다음 단계로 간다.

### 1. 기획

`plan` 의 원칙 그대로 **범위를 깎는다.** "그건 다음에 추가할 수 있어요"가 기본 대사다.
한 번에 하나만 묻고, 모르면 대신 정하고 확인만 받는다. 기술 용어를 쓰지 않는다.

`docs/기획서.md` 맨 아래 `## 추가 기능` 절에 이어서 적는다. (절이 없으면 만든다)

```markdown
### <기능 이름> (YYYY-MM-DD)
- 왜: 누가 어떤 불편 때문에 쓰는가 (한 줄)
- 화면: 새로 생기거나 바뀌는 화면 (최대 2개)
- 저장할 것: 새로 저장하는 것 (없으면 "없음")
- 하지 않는 것: 이번에 안 넣기로 한 것
- 확인할 것: QA에서 눌러볼 시나리오 3개 이내
```

"확인할 것"은 개발 단계에서 테스트로 먼저 옮겨지고, QA 단계의 체크리스트가 된다. 여기서 사용자와 합의한다.
테스트로 옮길 수 있게 **누가, 무엇을 하면, 어떻게 되는지** 구체적으로 적는다. "리뷰가 잘 된다" 가 아니라 "로그인 안 한 사람에게는 리뷰 쓰기 버튼이 안 보인다".

### 2. 디자인

- 새 화면은 `design-system/*/MASTER.md` 와 기존 화면의 컴포넌트·간격·글꼴을 **그대로** 쓴다. 새 색을 만들지 않는다.
- 기본 디자인(Your Next Store 스타일)으로 만든 서비스면 `design` 스킬의 `references/yns/` 에서 비슷한 화면을 찾아 옮긴다.
- 필요한 shadcn 컴포넌트가 없으면 그것만 `npx shadcn@latest add <이름>` 으로 받는다.
- 먼저 **가짜 데이터로 화면만** 만들고, 데스크톱과 모바일 폭(390px) 스크린샷을 보여준다.
  "이 모양으로 갈게요, 괜찮으세요?" 확인을 받는다.

### 3. 개발

**테스트부터 쓴다.** 디자인 확인이 끝난 뒤, 실제 데이터를 붙이기 전에 위 **테스트 먼저 (TDD)** 순서대로.

- 기획서 "확인할 것" 시나리오를 하나씩 테스트로 옮긴다. 로그인 없이 되는 흐름은 `e2e/<기능>.spec.ts`,
  로그인·권한이 걸린 것은 가짜 사용자(로그아웃 / A / B)로 서버 액션을 부르는 Vitest 테스트로. 예: B가 A의 리뷰를 지우려 하면 거절된다.
- 저장·권한·금액처럼 틀리면 안 되는 로직은 Vitest 테스트를 먼저 쓴다.
- 전부 돌려 실패를 확인하고 나서 아래 규칙대로 만든다. 테스트를 하나씩 통과시켜 나간다.

- 저장할 것이 늘면 `build` 스킬의 "Supabase MCP 사용 규칙" 순서대로 한다.
  `apply_migration` (같은 SQL을 `supabase/migrations/` 에도 저장) → `list_tables` → `get_advisors` → `generate_typescript_types`.
- **새 테이블에는 RLS를 반드시 켜고** 정책과 GRANT를 같이 만든다 (GRANT가 없으면 `42501` 오류. `build` 스킬 3단계 참고). 남의 데이터를 읽거나 고칠 수 없는지가 기준이다.
- **쓰고 있는 컬럼·테이블은 지우거나 이름을 바꾸지 않는다. 추가만 한다.** 데이터베이스는 실제 사이트와 같이 쓰기 때문에,
  마이그레이션을 적용하는 순간 아직 옛 코드인 실제 사이트가 깨진다. 지우는 일은 새 코드가 배포된 뒤 별도 요청으로 한다.
- 기존 데이터를 고치거나 지워야 하면 사용자에게 먼저 묻는다.
- 비밀 키가 새로 필요하면 `.env.local` 에만 넣고, 배포 때 Vercel 환경변수에도 넣어야 한다고 적어둔다.
  `NEXT_PUBLIC_` 은 브라우저에 보여도 되는 값에만 붙인다.
- 결제·환불과 닿으면 `pay` 스킬의 규칙(서버에서 금액 대조, 시크릿 키는 서버에서만)을 그대로 지킨다.
- 가짜 데이터를 실제 데이터로 바꾼다. 가짜 데이터 파일이 남지 않게 정리한다.

### 4. QA

아래 **검증**의 기본 검증과 큰 기능 검증을 모두 돌린다.
기획서의 "확인할 것" 시나리오마다 어떻게 확인했는지와 결과를 표로 보여준다.

```
| 확인할 것 | 확인 방법 | 결과 |
|---|---|---|
| 로그인한 사람만 리뷰를 쓸 수 있다 | 자동 테스트 | 통과 |
| 남의 리뷰는 지울 수 없다 | 자동 테스트 + 데이터 확인 | 통과 |
| 모바일에서 별점을 누를 수 있다 | 자동 테스트 + 스크린샷 | 통과 |
```

## 검증

**사용자가 시키지 않아도 항상 돌린다.** 통과하기 전에는 "다 됐어요"라고 말하지 않는다.

### 기본 검증 (작은 수정, 큰 기능 모두)

```bash
npx tsc --noEmit
npm run lint
npm test
npm run test:e2e
npm run build
```

- 하나라도 실패하면 고치고 처음부터 다시 돌린다. (`package.json` 에 `lint` 스크립트가 없으면 그 줄만 건너뛴다)
- 테스트는 **이번에 쓴 것만이 아니라 전부** 돌린다. 예전 기능이 깨졌는지 여기서 잡힌다.
- `npm run dev` 를 띄우고 `agent-browser` 로 바뀐 화면을 연다 (`next-dev-loop` 의 방식).
  - 데스크톱 폭과 모바일 폭(390px) 스크린샷을 찍어 직접 본다. 깨진 곳이 없는지, 요청한 대로 바뀌었는지.
  - 브라우저 콘솔에 에러가 없는지 본다.
- 바뀐 화면을 쓰는 핵심 흐름이 여전히 되는지 한 번 눌러본다. 예: 상품 카드 문구를 바꿨으면 상품 상세로 넘어가는지.

### 큰 기능 검증 (추가)

- 기획서의 "확인할 것" 시나리오가 전부 테스트로 있고 통과하는지 본다. 빠진 게 있으면 테스트부터 추가한다.
  화면 모양은 테스트가 못 잡으니, 새 화면은 `agent-browser` 로 한 번 끝까지 눌러보며 스크린샷으로 본다.
- 권한을 확인한다. 로그아웃 상태, 다른 사용자로 접근했을 때 막히는지. (테스트의 가짜 사용자 로그아웃 / A / B, 그리고 아래 `execute_sql` 로 실제 RLS)
- DB를 바꿨으면 Supabase MCP의 `get_advisors` (security, performance) 경고가 없어야 한다.
- 시나리오를 눌러본 뒤 `execute_sql` (읽기만)로 데이터가 의도대로 저장됐는지 직접 본다.
  예: 리뷰를 쓰고 나서 `reviews` 에 행이 생겼는지, 다른 사람 계정으로는 안 보이는지.
- **기존 핵심 흐름이 안 깨졌는지** 처음부터 눌러본다. 랜딩 → 로그인 → 상품(요금제·예약) 선택 → 테스트 결제 승인.
  결제와 닿지 않은 기능이어도 한다. 공용 컴포넌트를 건드리면 엉뚱한 곳이 깨진다.
  결제창은 자동 테스트가 못 들어가므로 이 흐름은 `agent-browser` 로 직접 누른다.
- `web-design-guidelines` 로 새 화면을 훑는다.

### 실패했을 때

- Playwright 테스트가 실패하면 추측하기 전에 `npx playwright show-report` 의 실패 화면 스크린샷과 trace 부터 본다.
- 데이터베이스와 닿는 오류면 추측하기 전에 Supabase MCP `query_logs` 로 로그부터 본다.
- 고치고 검증을 처음부터 다시 돌린다. 같은 문제로 세 번 실패하면 멈추고,
  무엇이 안 되는지와 시도한 것을 사용자에게 쉬운 말로 설명한 뒤 어떻게 할지 묻는다.
- 검증을 건너뛰거나, 실패한 채로 커밋하지 않는다. `--no-verify` 도 쓰지 않는다.

## 끝

검증을 통과하면 커밋한다. 커밋 메시지는 한국어로 무엇을 바꿨는지 한 줄.

```bash
git add -A && git commit -m "<무엇을 바꿨는지>"
```

`/build` 가 깔아둔 커밋 검사기가 비밀 키를 한 번 더 막는다.

**푸시는 묻고 한다.** Vercel이 GitHub와 연결돼 있으면 푸시하는 순간 실제 사이트가 바뀐다.

```
다 됐어요. 확인한 것: (검증 결과 요약)
실제 사이트에도 올릴까요? 올리면 1~2분 뒤에 반영돼요.
```

새 비밀 키를 추가했으면 푸시 전에 Vercel 환경변수에 넣었는지 먼저 확인한다. 없으면 배포된 사이트만 깨진다.
